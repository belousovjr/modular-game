# Назначение проекта

Это основа браузерной игры на Babylon.js и TypeScript. Сеттинг и жанр пока не выбраны. Проект развивается вайбкодингом, в том числе несколькими людьми или агентами. Сохраняй возможность добавлять фичи независимо. Не добавляй сюжет, игровые системы или универсальные абстракции без задачи.

## Обязательное направление: будущий мультиплеер

Каждое решение по умолчанию учитывает будущий авторитетный сервер. «Пока локально» не оправдывает смешивание симуляции, ввода и визуализации. Серверного кода, БД и реальной сети сейчас нет; не заявляй, что мультиплеер уже реализован.

- `src/simulation/` — headless TypeScript: без Babylon, DOM, localStorage, браузерных таймеров и импорта клиентского core. Этот код должен запускаться в Node. Проверка импортов автоматизирована; запрет браузерных глобальных API также соблюдай при ревью.
- Истиной о мире владеет authority. Клиент отправляет намерения/команды, получает сериализуемые снимки и отображает их. Ввод, UI и меши не меняют авторитетное состояние напрямую. Меш никогда не является хранилищем игровой истины.
- Сейчас authority содержит только часы, поскольку игровой механики нет. Первая игровая фича должна добавить явный JSON-совместимый протокол команд и снимков. Не отправлять функции, классы Babylon или ссылки на объекты между слоями.
- Команды валидируются на стороне authority: структура, конечные числа, диапазоны, допустимость действия. Когда появятся игроки — проверять владельца и права, последовательность, дубликаты, устаревание и частоту. Клиентскому времени и клиентским результатам не доверять.
- Первая сетевая реализация заменяет локальный адаптер authority удалённым; рендер и ввод не должны зависеть от местонахождения симуляции. На этом этапе нужны асинхронная доставка, идентичность игроков, reconnect и сверка состояния. Не прятать синхронный доступ к изменяемому миру в API модулей.
- Объекты мира получают стабильные сериализуемые ID от authority. Локальные настройки модулей не определяют правила общей сессии: сетевой сервер утверждает набор, конфигурацию и совместимость игровых модулей. Клиентские визуальные модули могут оставаться персональными.
- Случайность игрового мира должна иметь явный seed и состояние генератора. Запрещён неуправляемый `Math.random()` внутри симуляции. Порядок выполнения систем явный. Babylon-физика не предполагается детерминированной между машинами; не обещай lockstep без доказательства.
- Предсказание клиента и интерполяция — отдельный слой отображения, добавляются по реальной потребности. Не дублировать игровые правила в UI.

## Время

- Симуляция использует фиксированный шаг 60 Hz и целочисленный tick; время выводится из tick. FPS рендера не определяет скорость игры. Скорости выражаются в единицах/секунду.
- Локальные часы получают разницу монотонного `performance.now()` снаружи headless-логики. Внутри симуляции нет скрытого чтения времени. При переносе на сервер источник времени заменяется.
- Нельзя обрезать `delta` с потерей времени или выбрасывать задолженность тиков ради FPS. Текущий лимит работы — 240 тиков за вызов; задолженность сохраняется и показывается в UI. При дорогой симуляции потребуется отдельный worker/сервер и политика восстановления, а не тихое замедление.
- Замороженная вкладка не может выполнять код. После возобновления локальная сессия догоняет время. Реальное непрерывное выполнение обеспечит будущий сервер. Перерыв между вызовами не означает паузу игры.
- Игровой режим пока отсутствует; будущий режим игры должен быть отдельным модулем. Запуск симуляции определяется выбранным модулем, независимо от наличия игрового режима; применение набора модулей пересоздаёт сцену. В мультиплеере локальный редактор/меню не останавливает сервер.
- Сетевые сроки и реальные даты позже опираются на серверные часы. `Date.now()` клиента не определяет игровые исходы.

## Структура и модули

- `src/core/` — движок, сцена, контекст, менеджер модулей, настройки. Core не импортирует игровые модули.
- Локальные инструкции: `src/core/AGENTS.md` для core и `src/modules/<id>/AGENTS.md` для каждого модуля. Перед изменением читать соответствующий файл. При изменении назначения, поведения, API, зависимостей, жизненного цикла или сценариев тестирования актуализировать его в том же изменении; при создании модуля создавать и его `AGENTS.md`. Обновление инструкций — часть завершения задачи, отдельное напоминание не требуется.
- В корневом `AGENTS.md` хранить общие правила проекта; в локальных — актуальные контракты, зависимости и ограничения соответствующей части. Не дублировать общие правила и не описывать конкретные модули в корневом файле. При изменении общего правила обновлять корневой файл.
- `src/modules/<id>/index.ts` или `index.tsx` — публичное определение модуля. Остальные файлы каталога приватные. Межмодульные импорты только через `index.ts` / `index.tsx`; API экземпляров только через `deps`.
- `src/registry.ts` — явная регистрация и стартовый набор. Добавление каталога само по себе модуль не включает.
- Модуль объявляется через `defineModule`, с постоянным уникальным ID, названием, категорией `category`, `requires` и `setup`. Тип `deps` выводится из `requires`; не использовать `any`, приведения типов и глобальный реестр для обхода ограничения. Техническое приведение внутри менеджера — единственная точка стирания типов.
- Зависимости — ациклический граф. Менеджер проверяет граф до запуска, запускает зависимости первыми, останавливает в обратном порядке. Одинаковый ID не заменяет совпадение зарегистрированного определения.
- Все созданные ресурсы немедленно регистрируются через `scope.onDispose`: подписки, меши, материалы, обработчики, таймеры, панели. Очистка обязательна при частичном неудачном запуске. `setup` сейчас синхронный; не запускать бесконтрольные async-задачи из него.
- Общение: явные команды/запросы через публичный API, события через существующие Babylon Observable там, где они подходят. Не создавать глобальную шину событий без необходимости.
- Если решение уже есть в core или Babylon, использовать его. Не строить в модуле собственный параллельный движок, цикл рендера или систему управления ресурсами.
- Обязательность игровой фичи не делает её частью core. Переносить в core только общую инфраструктурную ответственность; оптимизировать по измерениям.
- Когда появятся headless игровые системы модулей, выделить их в явно серверно-совместимые entry points и дополнить проверку границ. Не передавать Scene в симуляцию и не запускать клиентский setup на сервере.

## UI и конфигурация

Для разметки интерфейса использовать React и TSX, готовые компоненты Radix Themes и иконки Lucide. Не переопределять их оформление своим CSS; CSS оставлять для геометрии сцены и размещения окон. Один React root приложения; core хранит регистрации панелей, а React отображает и размонтирует их при остановке модуля. Не создавать roots в модулях. Сохранять доступность: компоненты кнопок и чекбоксов библиотеки, подписи, клавиатура, видимый фокус, ошибки текстом. Рендер-цикл не должен пересоздавать UI.

Инфо-панели — инфраструктура core: модуль регистрирует React-содержимое через `core.panels.register`, очистку — через `scope.onDispose`. Кнопка «Детали» доступна для запущенного модуля с зарегистрированной панелью; закрытие окна не останавливает модуль.

Галочки включают зависимости автоматически; зависимость с активными потребителями выключить нельзя. `required`-модули включены всегда. Изменения галочек и статусов применяются и сохраняются сразу. При изменении включённого набора сцена пересоздаётся; горячая замена не реализована. Кнопки применения нет; сброс возвращает стартовый набор и рабочие статусы модулей, сбрасывая камеру.

В localStorage только версионированная персональная конфигурация ID модулей, видимости и положения окон, положения камеры, не игровой мир. Проверять неизвестные и повреждённые данные; ошибки доступа к storage не должны ломать приложение. Стартовый набор хранится в Git. Любая будущая персистенция мира требует отдельной схемы и миграций.

## Работа в команде

Перед изменением API найти потребителей и обновить их вместе с тестами. Делить работу по модулям; изменения core и публичных контрактов согласовывать явно в описании изменения. Не редактировать соседние проекты.

Не добавлять DI-контейнер, ECS, свой UI-фреймворк, автопоиск плагинов, версии плагинов или сетевую инфраструктуру без конкретной задачи. Имитатор сети пока отсутствует. Добавить его, когда появятся игровые команды: задержка, джиттер, потери и перестановка сообщений должны проверять реальный протокол и восстановление, а не декоративные таймеры.

Минимальные обязательные проверки: `npm run check`, `npm test`, `npm run build`. При изменении менеджера покрыть порядок зависимостей, циклы и очистку при ошибке; при изменении симуляции — одинаковый результат при разных FPS, длинный перерыв и проверку команд. Типовые ограничения проверяются отрицательными тестами `@ts-expect-error`.

Сначала наименьшее полное решение. Комментарий об осознанном пределе: `shortcut: <предел>, <когда пересмотреть>`.

Клиентские сценарии тестирования модулей используют отдельный scope, не обходят authority и не меняют правила симуляции. Контракты runner и автоматизированного запуска описаны в `src/core/AGENTS.md`, конкретные сценарии — в инструкциях модулей.
