# Мультиплеер

Статус на 21 ноября 2026 года — план реализации. Первый результат: два браузера входят в одну комнату, независимо управляют героями, видят движение друг друга и восстанавливают подключение после разрыва.

## Размещение

| Где | Ответственность |
| --- | --- |
| Vercel | Vite-клиент и HTTP API. По мере необходимости — выдача короткоживущего билета входа в комнату. |
| Долгоживущий Node.js-процесс | Авторитетная комната, часы 60 Гц, обработка ввода, снимки и WebSocket. Начать с одного процесса в одном регионе. Локально тот же процесс запускается рядом с Vite. |
| Neon PostgreSQL | Долговременное хранение после появления схемы мира. Подключение через серверный `pg` уже проверяется маршрутом `/api/db-health`. Контрольные точки сохраняются вне горячего цикла тиков. |

WebSocket в Vercel Functions общедоступен с октября 2026 года. Соединения ограничены временем выполнения функции, а два клиента одной комнаты могут попасть в разные экземпляры. Для комнаты с одним владельцем и непрерывной симуляцией выбираем долгоживущий процесс. В продакшене браузер подключается к его WSS-адресу напрямую. Публичный адрес сокета передаётся клиентской конфигурацией Vite, строка подключения к базе остаётся на сервере. Хост и регион игрового процесса выбираются перед первым публичным развёртыванием. [Выпуск WebSocket](https://vercel.com/changelog/websocket-support-is-now-generally-available) · [Распределение подключений по экземплярам](https://vercel.com/kb/guide/build-a-real-time-chat-app-with-websockets) · [Драйверы Neon](https://neon.com/docs/connect/choose-connection)

## Первая комната

1. **Запустить authority в Node.** Загрузить совместимые данные коллизий текущего участка и создать один экземпляр headless-часов на комнату. На старте проверить, что сборка коллизий Chicago Loop воспроизводима в Node и совпадает с клиентской. Переиспользовать `characters/headless.ts`, передавая отдельные серверные ID, владельцев и стартовые позиции. Для первой проверки достаточно движения двух героев по общей статической карте. Состав игровых модулей утверждает комната.
2. **Подключить два клиента.** Ввести версионированные JSON-сообщения поверх одного WebSocket. Вход возвращает ID комнаты, эпоху комнаты, ID игрока, версию мира и полный снимок. Онлайн-снимок несёт серверный tick, позы героев и подтверждение ввода текущего клиента. Полные снимки передаются с начальной частотой 20 Гц, симуляция работает на 60 Гц. Так любой свежий снимок восстанавливает представление после пропуска. Выборки по области интереса, дельты и бинарный протокол добавлять по измерениям.
3. **Подключить интерфейс и восстановление.** Добавить чекбокс «Мультиплеер» в панель «Симуляция». При включении локальная игра остаётся активной до первого совместимого снимка. При ошибке входа показать причину и оставить локальный режим. В онлайне ввод идёт в удалённый адаптер, а Babylon читает его снимки. Временный разрыв держит последние позы, показывает статус и запускает повторный вход с backoff и джиттером. Возвращение в локальную игру закрывает сокет и отменяет повторные попытки. Пересоздание клиентской сцены не сбрасывает серверную комнату. На первом этапе игровые машины и NPC в онлайн-комнате выключены.
4. **Проверить движение и затем добавить предсказание.** Первая сквозная проверка использует снимки сервера. После неё внедрить интерполяцию удалённых героев и предсказание своего героя как отдельный слой представления. Прогнать одинаковые сценарии на прямом подключении и с имитатором доставки.

### Вход, команды и восстановление

- Для локальной проверки сервер выдаёт отдельный случайный токен возобновления каждому клиенту. Вкладка хранит его в `sessionStorage`, чтобы перезагрузка восстанавливала игрока. Проверить также дублирование вкладки: политика комнаты допускает один активный сокет на токен. Прежний сокет перестаёт принимать команды после успешного возобновления. До публичного деплоя добавить проверяемый билет входа, allowlist Origin и лимиты подключений и входящих сообщений. Токены передавать внутри защищённого соединения и исключить из логов.
- Команда содержит намерение движения, sequence и наблюдаемый tick. Владелец определяется сокетом. Authority валидирует формат, конечность чисел, диапазоны, частоту, последовательность и допустимость на текущем тике. Фактический тик применения назначает сервер. Для залипшего ввода использовать существующий TTL. При разрыве прекратить движение и на ограниченное время сохранить место игрока для возобновления.
- Ввод по сети сначала передаётся как существующие периодические управляющие команды. Моментальные действия, например прыжок, должны иметь однозначную семантику повторов. Квитанция сообщает, обработал ли сервер команду, а снимок подтверждает серверное состояние и последнее принятое намерение. После reconnect ждать полного снимка, сбросить буферы, восстановить sequence по серверному подтверждению и отправить свежий ввод. Старые кадры предыдущего соединения и другой эпохи комнаты отбрасывать.
- WebSocket надёжен и упорядочен, поэтому задержанный TCP-пакет может задержать последующие снимки. Следить за `bufferedAmount` и ограничивать очереди. У медленного клиента пропускать старые снимки ещё до `send`, затем отправлять свежий полный снимок. Систематически отстающее соединение закрывать с возможностью возобновления. Реальные условия WebSocket отдельно проверять разрывом и задержкой TCP. Имитатор потерь и перестановок на уровне сообщений проверяет устойчивость протокола. [MDN о bufferedAmount](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/bufferedAmount)

### Сглаживание и сверка

- **Другие игроки.** Буферизовать снимки по тикам. Рисовать между двумя снимками на немного отложенной серверной шкале. Начать с 100–150 мс буфера при 20 Гц и откалибровать по джиттеру и числу исчерпаний буфера. Для позиций достаточно линейной интерполяции, для угла — кратчайший поворот. Если свежих снимков нет, держать последнюю позу. Сбрасывать историю при телепорте, повторном появлении персонажа и смене эпохи. [Gambetta о движении удалённых игроков](https://www.gabrielgambetta.com/entity-interpolation.html) · [Fiedler о буфере снимков](https://gafferongames.com/post/snapshot_interpolation/)
- **Свой игрок.** Немедленно показать локальный результат ввода через тот же headless-шаг персонажа. Хранить ограниченную историю ввода по тикам. При снимке восстановить состояние на серверном тике, удалить подтверждённые команды и повторно просчитать оставшиеся локальные тики. Поскольку ввод удерживается несколько тиков, для восстановления нужны активное намерение, срок его действия и прочее скрытое состояние шага. Текущий `CharacterSnapshot` предназначен для отображения и сам по себе для полного повторного шага недостаточен. Малое расхождение гасить только в камере и меше, большое применять сразу. [Gambetta о предсказании и сверке](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html)
- **Часы клиента.** Оценивать серверный tick по снимкам и RTT от ping/pong с монотонными локальными часами. RTT служит визуализации и диагностике. Authority применяет команды по собственным часам, клиент не выбирает исходный тик действия. Компенсация задержки с перемоткой сервера понадобится только при появлении механики, для которой она нужна.

## Двери, машины, NPC и сохранение

После приёмки двух игроков переносим состояние двери и машины в комнату. Сервер определяет владельца и допустимость действий, клиенты получают углы створок, позы и скорость. Cannon работает на authority, удалённые машины отображаются по снимкам. Предсказание за рулём рассматривается после замеров.

Один NPC-планировщик на комнату ведёт общие маршруты и столкновения по авторитетным позам игроков. Камера участвует в выборе данных для конкретного клиента. Фоновые NPC передаются компактными сценариями с seed и версией навигации, при взаимодействии клиент получает новую ревизию и снимки. При reconnect клиент получает текущие режимы NPC своей области. См. [контракт NPC](../src/modules/npcs/AGENTS.md).

Neon подключаем к игровому состоянию после определения состава контрольной точки и правил восстановления. Публичные снимки оптимизированы для отображения. Для восстановления нужны также версия правил и карты, серверный tick, состояние генератора, активные состояния сущностей и резервы NPC. Обновление контрольной точки транзакционно, частота записи определяется допустимой потерей прогресса. Миграции проверять на отдельной ветке Neon до применения к production.

## Приёмка

- Два независимых браузерных контекста входят в одну комнату. У каждого свой ID; оба видят движение другого. Успешный вход через чекбокс переключает сцену, ошибочный оставляет локальную игру доступной. При выходе одного клиента второй продолжает движение.
- Автоматизированный тест с двумя настоящими сокетами проверяет доставку, отклонение чужого ID, повторов и устаревших команд, остановку при разрыве, возобновление с полным снимком и очистку ресурсов.
- Проверить 0, 100 и 200 мс RTT, джиттер и паузу доставки. Записывать RTT, задолженность тиков, частоту снимков, исчерпание буфера, величину сверки и размер очереди сокета. При одинаковом серверном вводе результаты authority совпадают при разных FPS клиентов.
- Перед публичным включением проверить Vercel preview с настоящим WSS endpoint, два браузера из разных сетей, разрыв и повторный вход после перезапуска процесса. При рестарте без сохранения новая эпоха комнаты должна явно сбрасывать клиентское состояние.
- Проверить `npm run check`, `npm test` и `npm run build`.
