# Modular Game

Локальная основа игры без выбранного сеттинга: Babylon.js, TypeScript, Vite, React UI на Radix Themes с иконками Lucide. Поддерживаются локальная симуляция и первая онлайн-комната для персонажей. Серверный маршрут проверяет подключение к Neon PostgreSQL.

Направление развития, границы будущих модулей и этапы постоянного онлайн-мира на основе Чикаго — в [черновике плана](docs/PLAN.md).

## Запуск

Node.js 24.12+:

```sh
npm ci
npm run dev
```

Открыть http://127.0.0.1:5175. Кликнуть по сцене для фокуса. Удерживать ПКМ и двигать мышь — смотреть вокруг; WASD — свободно летать по направлению взгляда, Q/E — спуск/подъём, Shift — ускорение. Скорость 40 единиц/с, с Shift — 160. Колесо перемещает камеру вперёд/назад; орбитального центра и ограничения радиуса нет. Положение и направление сохраняются, старый орбитальный обзор переносится автоматически.

```sh
npm run check
npm test
npm run build
npm run preview
```

## Вход в игру

`npm run dev` запускает Vite и игровую комнату вместе. Откройте `http://localhost:5175/play`, зарегистрируйтесь по почте, создайте персонажа и выберите его. В игре доступны WASD после фокуса на сцене и выход к списку персонажей. Поверх сцены показаны FPS и состояние подключения. Сутки на /play синхронизированы по часам комнаты и длятся два реальных часа. Лаборатория с панелями остаётся на `/`.

Neon Auth хранит аккаунты и сеансы в `neon_auth`, миграция `npm run db:migrate` создаёт `public.characters` со ссылкой на аккаунт. У одного аккаунта может быть несколько персонажей. Каждый персонаж управляется одним подключением одновременно. Временный разрыв или перезагрузка восстанавливают выбранного персонажа, пока сессия действительна.

Веб-приложению и игровому процессу нужны `DATABASE_URL`, `NEON_AUTH_BASE_URL` и `NEON_AUTH_JWKS_URL` одной ветки. Для миграций нужен `DATABASE_URL_UNPOOLED`. Локально эти переменные подтягивает `neon deploy`. Для Vercel дополнительно задать `VITE_GAME_WS_URL` с публичным WSS-адресом Node-процесса и добавить Origin деплоя в Neon Auth и `GAME_ORIGIN` игрового процесса. По умолчанию комната слушает `127.0.0.1:5177/room`. При смене порта задать `GAME_PORT` и `VITE_GAME_WS_URL`.

Онлайн использует фиксированный профиль окружения Чикаго и управления. Входные двери зданий общие для игроков. Neon хранит контрольные точки створок по `GAME_ROOM_ID` (по умолчанию `local`) и версии карты. На один ключ запускается один процесс authority. В комнате доступны общий автомобиль и NPC. После применения миграции `003-world-npcs.sql` через `npm run db:migrate` сиды NPC и остановившиеся повреждённые машины сохраняются по идентификатору комнаты и версии навигации. Сохранение позы героя после рестарта остаётся отдельной задачей. Тест живых сокетов — `npm run test:online`. Замер нагрузки комнаты — `npm run bench:room`. [Результаты и методика](docs/PERFORMANCE_BASELINE.md#серверная-комната-chicago-loop). См. [план мультиплеера](docs/MULTIPLAYER.md).

## Neon PostgreSQL

`neon deploy` применяет конфигурацию `neon.ts` к связанной ветке и подтягивает параметры подключения. Сервер читает pooled `DATABASE_URL` из `.env.local`, `.env` или окружения. Для Vercel задайте `DATABASE_URL` в окружении проекта.

Проверка после запуска `npm run dev`:

```sh
curl --fail-with-body http://127.0.0.1:5175/api/db-health
# {"ok":true,"database":"postgres"}
```

Маршрут выполняет `SELECT 1` и возвращает HTTP 503, если подключение отсутствует или недоступно. Игровые таблицы и сохранения будут добавлены вместе с первой схемой мира.

## Что уже есть

- Сцена на весь экран, FPS и кнопка «Модули» с закреплённым справа списком категорий; изменение набора сразу пересоздаёт сцену. Игровой режим пока отсутствует, позже он станет отдельным модулем.
- Изменения галочек и статусов применяются сразу; пояснения зависимостей доступны при наведении. Успешное сохранение не создаёт уведомлений, ошибки остаются видимыми.
- Чекбоксы модулей, автоматическое включение зависимостей, запрет отключения используемой зависимости, немедленное сохранение набора в localStorage.
- Кнопка «Детали» у запущенного модуля с инфо-панелью: перемещаемое окно с закрытием. Панель симуляции показывает секунды, тики и задолженность.
- Типизированные зависимости, проверка графа, обратная очистка и обработка неудачного setup.
- Два примера: площадка и зависимый от неё маяк. Его визуальная анимация следует снимку часов симуляции.
- Опциональный модуль симуляции (включён по умолчанию): headless local authority с фиксированными 60 Hz. Задолженность после зависания сохраняется, за кадр обрабатывается не более 240 тиков. Низкий FPS не меняет скорость часов после догоняния.

## Геометрия

Модуль «Геометрия» в категории «Рендеринг» зарегистрирован вне стартового набора. Предоставляет API для потребителей; при включении видимые объекты не появляются. Собственного сценария ▶ нет.

Потребитель объявляет `requires: { geometry: geometryModule }` и вызывает `deps.geometry.createModel(name, parts, scope)`. Деталь содержит имя поверхности `surface`, размер `size: [x,y,z]` и необязательные локальные `position`/`rotation` (радианы). Результат содержит корень `root` и группы мешей `surfaces`. Геометрия общая, преобразования независимы; простое отображение работает без света. Пока поддержаны только прямоугольные детали. Это клиентское представление, не игровое состояние. Контракт — в [инструкции модуля](src/modules/geometry/AGENTS.md).

Независимый `materials` зависит от `geometry`: включает общие материалы с физическим масштабом фактуры 2 м на повтор и mipmaps для детализации по размеру на экране. Автоматический выбор LOD выполняет `object-rendering`; статичные дорожные поверхности уже объединяются через thin instances.

## Шаблоны объектов

«Шаблоны объектов» (`object-templates`) — функциональный модуль категории «Рендеринг», зависит от «Геометрии» и зарегистрирован вне стартового набора. Каталог пуст до регистрации контентным модулем; включение не создаёт объектов, собственного ▶ нет.

Потребитель объявляет `requires: { templates: objectTemplatesModule }`, регистрирует через `deps.templates.register(definition, scope)` определение с `id`, `version`, числовыми `parameters` (`default`, `min`, `max`) и чистым синхронным `build(parameters)`. Рецепт возвращает `{hideDistance, levels: [{distance, parts}]}` с деталями геометрии. `resolve(id, parameters)` возвращает проверенное JSON-описание без мешей; `createModel(id, name, parameters, scope, level = 0)` создаёт выбранный уровень и возвращает `{template, model}`. Контракт — в [инструкции модуля](src/modules/object-templates/AGENTS.md).

Этот модуль только описывает уровни и дальность; автоматическое переключение и исчезновение выполняет `object-rendering`. Примеры здания и столба существуют только в автоматических тестах.

## Отрисовка объектов

«Отрисовка объектов» (`object-rendering`) зависит от шаблонов и геометрии, зарегистрирован вне стартового набора, не содержит контента и сценария ▶. Потребитель вызывает `deps.rendering.createObject(templateId, name, parameters, scope, mobility?, batchMaterialOrSurface?)`, размещает возвращённый `root`; `level()` показывает выбранный индекс или `null`. Перед кадром автоматически выбирается один LOD, при достижении `hideDistance` все уровни выключаются.

Расстояние считается до общей мировой границы всех уровней с учётом преобразований объекта. По умолчанию используется активная камера. `setDistanceSource(() => heroPositionOrNull, scope)` подключает отображаемую позицию героя; `null` скрывает объекты без подстановки камеры. `getDistanceOrigin()` даёт эту же точку будущей загрузке мира. Сетка X/Z отбирает кандидатов по размерам и дальности объектов. По умолчанию dynamic отслеживает преобразования автоматически; мир использует static, и после последующих правок статичного корня нужен `refreshTransform()`. `getStats()` показывает кандидатов, пересчёты границ и пакеты. Необязательный batchMaterial (либо имя поверхности) объединяет static-экземпляры с одной прямоугольной деталью на LOD по материалу и ячейке; world использует это для дорог, тротуаров и бордюров. На пакетном пути материал задаётся явно, onModelCreated не вызывается. Посещённые уровни кешируются до удаления экземпляра; скрытие не освобождает их память и не меняет состояние authority. Контракт — в [инструкции модуля](src/modules/object-rendering/AGENTS.md).

## Первый сгенерированный квартал

Включить **«Первый квартал»** в категории «Окружение»: появится игровая адаптация River North 1088×1136 м: четыре связанных участка, 23 улицы (четыре магистрали шириной 24 м, остальные — 6 м), тротуары, бордюры, 1405 зданий, 1905 фонарей и авторской площадью. ▶ облетает центральную часть уже существующего участка, не добавляя объекты. Около 75% зданий должны быть скрыты дальностью; фактические hiddenFractionMin/Max сохраняются в diagnostics сценария world в FPS-отчёте. Для чистого вида старые маяк и площадку можно отключить вручную. Стартовый набор не изменён.

`world-generation` — функциональный генератор без сценария ▶. Чистый TypeScript entry point в `src/modules/world-generation/headless.ts` проверяет схему, использует явный seed и возвращает JSON-размещение. `world` хранит схему и определения шаблонов, размещает результат через `object-rendering`. Улицы/тротуары/фонари генерируются, авторская вставка хранится отдельно и защищена reserved-зоной.

Свободные блоки заполняются несколькими домами с фасадами до 29 и высотами 8…27. Фонари: 4 детали до 25, один силуэт от 25 до 75, затем скрытие; шаг расстановки 20.

Первое ограничение: прямые отрезки улиц и одна плоскость высот с уклоном по X, без произвольного рельефа. Перекрёстки разбиты без наложения дорожных плит. Текстуры и теневые карты подключаются независимыми materials и shadows; статические коллизии предоставляет world.collision для headless-персонажа. Это адаптация River North, не точная копия Чикаго. Контракты — [генератор](src/modules/world-generation/AGENTS.md) и [квартал](src/modules/world/AGENTS.md).

## Добавить модуль

Создать `src/modules/<id>/index.ts` или `index.tsx`, объявить через `defineModule` из `src/core/context.ts`, указать `category` и `requires`, зарегистрировать в `src/registry.ts`. Публичный API возвращается из `setup`, чужой API доступен через `deps`. Все ресурсы регистрируются через `scope.onDispose` сразу после создания. См. площадку и маяк.

Core предоставляет `onFrame` (монотонная разница времени в миллисекундах, до рендера) и `panels`. Для своей инфо-панели передать React-элемент из `setup` и сразу зарегистрировать очистку: `scope.onDispose(core.panels.register('module-id', 'Название', <Info />))`. Core хранит регистрации панелей; React отображает кнопку «Детали», окно и содержимое внутри общей темы Radix, размонтирует панель при очистке. Оболочка UI — `src/main.tsx`, окно — `src/core/panel-window.tsx`. Оформление берётся из компонентов библиотеки, CSS отвечает только за размещение. Состояние и подписки содержимого принадлежат React-компоненту; подписки очищать в `useEffect`. Пример — `src/modules/simulation/index.tsx`. Видимость и положения окон сохраняются в localStorage и восстанавливаются при пересоздании сцены. Перемещение — за заголовок мышью/касанием или стрелками с фокусом на заголовке, закрытие — кнопкой или Escape.

Время доступно через объявленную зависимость `simulationModule` и `deps.simulation.snapshot()`. Маяк требует симуляцию, поэтому отключать её нужно вместе с маяком. Применение набора создаёт новые часы с нуля.

`npm run check` проверяет типы (включая отрицательные тесты) и границы импортов. Это защита от случайных нарушений, а не sandbox для недоверенного кода. Модули — доверенный исходный код проекта.

## Загрузка окружения

Подробные фасады, дорожная разметка и рецепты светофоров Чикаго запрашиваются по кварталам при приближении игрока или камеры. Стартовые данные включают грубую геометрию, коллизии и данные интерьеров. Сборка Vite сама генерирует файлы кварталов из исходной карты и упаковывает дорожные поверхности в точные инструкции восстановления вершин и граней.

## Сетевая симуляция

Перед запуском комнаты `npm run prepare:room` готовит кеш коллизий в `artifacts/room-map/`. Он запускается автоматически для `npm run dev` и `npm run dev:game`. Для самостоятельного запуска `node server/index.ts` сначала подготовьте этот кеш. Комната читает лёгкий манифест, подгружает данные возле игроков и автомобиля и освобождает редко используемые участки. Исходный JSON Чикаго нужен на этапе подготовки.

Одиночная игра и Node-комната используют фиксированные шаги и общие headless-правила персонажа и автомобиля. Сервер проверяет JSON-команды, рассчитывает позы и публикует снимки. Клиент сглаживает отображение и отправляет намерения. Профиль комнаты включает управление персонажем, автоматические входные двери и один общий автомобиль рядом с точкой появления. Нажмите E рядом с машиной для посадки. Кнопка «Автомобиль» в /play показывает управление и скорость.

`src/simulation` не зависит от браузера и Babylon. Клиентские ресурсы сокета принадлежат модулю simulation, серверный процесс запускается из `server/index.ts`. Текущий сетевой контракт, контрольные точки NPC и дальнейшие шаги описан в [плане мультиплеера](docs/MULTIPLAYER.md).

## Сценарии тестирования модулей

Клиентский сценарий `test` необязателен и сейчас задан у маяка и площадки (по 4 секунды), а также у world (10 секунд); перед каждым — 1 секунда прогрева: длительность `durationSeconds` и синхронный `setup({ core, deps, api, scope, report })`, возвращающий функцию `(progress) => void` с прогрессом от 0 до 1. Указывать `test` после основного `setup`, чтобы TypeScript вывел API экземпляра. `core` даёт доступ к сцене, кадровому событию и панелям, `api` — к своему запущенному экземпляру, `deps` — к объявленным зависимостям. `report(values)` сохраняет дополнительные конечные числовые показатели в `results[].diagnostics`; они не меняют FPS-метрики или правило допуска. Ресурсы и изменения теста очищаются через отдельный `scope.onDispose`, в том числе при неудачном старте. Сценарии выполняются существующим рендер-циклом; бесконтрольные async-задачи не нужны. Будущие игровые действия должны идти командами authority, а не менять мир из теста.

Кнопка ▶ появляется только у модулей со сценарием и запускает его; общий ▶ последовательно запускает доступные сценарии включённых модулей. Маяк демонстрирует двухкруговой облёт с изменением высоты и расстояния, площадка — круговой обзор. Управление камерой и основной UI заблокированы до окончания; кнопка «Остановить» остаётся доступной, включая клавиатуру. На время прогона core использует отдельную орбитальную камеру с прежними маршрутами; свободная камера и её управление возвращаются при завершении, отмене и ошибке. Скрытие вкладки отменяет прогон, чтобы фоновые ограничения браузера не искажали FPS. Часы симуляции продолжают идти.

Перед каждым замером — 1 секунда прогрева, которая входит в прогресс, но не в метрики. Измеряются интервалы реальных кадров: средний FPS = число кадров / время, минимум, максимум, медиана FPS, P95 времени кадра в миллисекундах (меньше — лучше), число кадров и измеренное время. На остановке сохраняется частичный результат. Для очереди под текущим прогрессом показывается общий: каждый сценарий занимает равную долю. После прогона панель закрывается крестиком без удаления данных из API; следующий запуск снова её показывает. Для нескольких тестов под таблицей выводится сводка по статусам, кадрам, времени, общему среднему FPS и крайним значениям. Средний FPS сводки считается по суммарным кадрам и времени, а не усреднением средних FPS тестов. Это FPS всей текущей сцены со всеми включёнными модулями и UI во время сценария, а не изолированная стоимость модуля. Результаты живут в памяти до следующего прогона или перезагрузки.

Для автоматизации доступен `window.moduleTests`:

```js
window.moduleTests.list();
await window.moduleTests.run(['beacon'], 10); // 10 с замера + 1 с прогрева
await window.moduleTests.run(); // все запущенные сценарии с их длительностями
window.moduleTests.getState(); // прогресс и сериализуемые результаты
window.moduleTests.stop();
```

Команда `test:modules` запускает Chromium без окна. Чтобы делегировать замер агенту или запустить из терминала, оставить `npm run dev` работающим и выполнить в другом терминале:

```sh
CHROME_BIN=/path/to/chromium npm run test:modules
# Если chromium есть в PATH, CHROME_BIN не нужен.
MODULE_TEST_IDS=beacon MODULE_TEST_SECONDS=10 npm run test:modules
# Для отладки с окном браузера:
node scripts/run-module-tests.mjs
```

Скрипт использует встроенные средства Node и DevTools Chromium, проверяет запуск и остановку кнопками, блокировку UI и прогресс, затем запускает выбранные сценарии и печатает JSON. `MODULE_TEST_URL` меняет адрес приложения (по умолчанию `http://127.0.0.1:5175`). Используется временный профиль с начальным набором модулей и размером viewport 1280×720; профиль удаляется после прогона. `MODULE_TEST_IDS` — ID через запятую; `MODULE_TEST_SECONDS` — длительность каждого замера от 0 до 300 секунд, не включая 0. Ошибка или отмена дают ненулевой код выхода.

Для сравнения FPS сохранять одинаковые браузер, разрешение, набор модулей и окружение. JSON включает разрешение и WebGL renderer: headless-прогон через SwiftShader измеряет программный рендеринг, его нельзя выдавать за производительность пользовательской видеокарты. Частота монитора и VSync тоже ограничивают FPS.

## Общий FPS-прогон

```sh
npm run test:fps
# Аппаратный замер с окном на том же ПК и в доступной графической сессии:
npm run test:fps -- --headed
```

Отдельно запускать dev-сервер не нужно: команда собирает production-версию и поднимает временный сервер на свободном порту. Используется Chromium из `CHROME_BIN`, PATH или установленного Linux-кэша Playwright. Если браузер не найден, указать `CHROME_BIN=/path/to/chrome`.

Команда включает и применяет **все зарегистрированные модули**, включая модули вне стартового набора, затем выполняет все доступные сценарии последовательно. Модули без собственного сценария тоже включены и влияют на производительность сцены. В терминале выводятся только средний FPS каждого сценария и общий средний FPS с цветами по шкале, PASS/FAIL, допустимые градации и renderer. Ошибки показываются отдельно. Полный отчёт версии 2 сохраняется в `artifacts/fps-report.json` (каталог исключён из Git), включая ошибки запуска.

Правило допуска хранится в `fps.config.json`:

```json
{
  "metric": "average",
  "passGrades": ["orange", "yellow", "green"]
}
```

Проверяется общий средний FPS по суммарным кадрам и времени, а не среднее арифметическое FPS сценариев. Градации общие с UI: `<30` — `red`, `30…<60` — `orange`, `60…<90` — `yellow`, `≥90` — `green`. Текущий конфиг пропускает средний FPS от 30; остальные метрики выводятся для информации и не определяют допуск. Градация определяется до округления. Для изменения допуска редактировать `passGrades`; пока поддерживается только метрика `average`.

Код выхода: `0` при успешных сценариях, наличии измерений и разрешённой градации; `1` при провале правила, ошибке, отмене, отсутствии замеров или некорректном конфиге. JSON содержит применённое правило `policy` и фактическую `grade`. Старый `FPS_MIN_AVERAGE` больше не используется. Автоматическую блокировку слияний нужно подключить к этому коду выхода в CI и настройках репозитория.

Для аппаратного прогона в текущем WSL-окружении проверена команда (переменные действуют только на процесс):

```sh
GALLIUM_DRIVER=d3d12 MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA MODULE_TEST_SECONDS=10 npm run test:fps -- --headed
```

Условия и ограничения исходного замера — в [базовой линии](docs/PERFORMANCE_BASELINE.md). Выбор драйвера выше относится к этому ПК/WSL, не является универсальной настройкой для всех ОС.

По умолчанию прогон headless. `--headed` запускает окно без разрешения на SwiftShader; фактический WebGL renderer всё равно нужно проверить в отчёте. JSON фиксирует `environment.headless`. Аппаратные замеры сравниваем на одном ПК, с одинаковыми GPU, браузером, графической сессией, питанием и разрешением; WSL/WSLg отмечаем отдельно от нативного Windows-браузера.

Изоляция: новый временный профиль браузера, viewport 1280×720; личный localStorage не меняется. `MODULE_TEST_SECONDS` переопределяет длительность каждого замера, но `MODULE_TEST_IDS` запрещён, чтобы прогон оставался полным. Сервер и браузер автоматически закрываются. Для сравнения веток использовать одинаковый runner и renderer: программный SwiftShader не является замером физической GPU.

Панель модулей разделена на вкладки «Рабочие», «Скрытые» (кандидаты в core, всегда включены) и «Архив» (кандидаты на удаление, всегда отключены). Меню троеточия меняет статус; вкладка и статусы сохраняются локально. Изменение состава сцены применяется сразу с её пересозданием; кнопки применения нет. Над вкладками находятся общий тест и сброс стартового набора, статусов и вкладки. Обзор камеры сохраняется при изменении модулей и между перезагрузками; сброс модулей возвращает камеру в исходное положение. Архивировать обязательные модули и зависимости включённых модулей нельзя. Скрытые и архивные не перечисляются в тултипах зависимостей. Статусы не переносят и не удаляют код.

Шестерёнка справа от «Модули» открывает экспорт/импорт персональных настроек в файлах `.mgeng` (обычный JSON внутри). Ctrl+Z отменяет изменения набора модулей и их статусов, Ctrl+Shift+Z возвращает их; история сохраняется в localStorage. Окна, категории и вкладки сохраняются автоматически и не входят в историю или признак несохранённых изменений. Ctrl+S сохраняет текущие настройки в IndexedDB. Звёздочка в начале заголовка страницы означает несохранённые изменения; после сохранения исчезает. Ошибки показываются текстом. Импорт обновляет localStorage, интерфейс и IndexedDB и может быть отменён. Экспорт включает только набор модулей и их статусы. Положение и видимость окон, вкладка, свёрнутые категории, камера, история и игровой мир в файл не входят; импорт сохраняет текущий интерфейс. Камера сохраняется отдельно только в localStorage, не участвует в undo/redo и не влияет на звёздочку; её сбрасывает только кнопка дефолтов. Во время тестов команды недоступны.


«Базовое освещение» (`lighting`): кнопка «Детали» открывает выбор времени суток и кнопки утра, дня, вечера и ночи. Положение, цвет и яркость солнца и подсветки вычисляются автоматически; время пока выбирается вручную. Настройки света действуют до пересоздания сцены, закрытие панели их сохраняет. Солнечные тени включаются отдельным модулем shadows.


Модуль «Материалы и текстуры» включается отдельно от мира. Он заменяет серое запасное оформление; выключение сохраняет геометрию. В «Деталях» — загрузка, ошибки и оценка памяти: 6 цветовых WebP 512² и 6 согласованных normal maps 512² с mipmaps, около 16 МиБ RGBA. Ресурсы взяты из chicago-test, происхождение и CC0 записаны в public/textures/city. Неудачная загрузка оставляет цвет поверхности. Фактура сохраняет масштаб на прямоугольных деталях любых размеров и поворотов, включая thin instances; mipmaps снижают детализацию по проекции на экран, но не выгружают память.

Корпуса домов сохраняют разметку граней: крыша остаётся серой и на дальнем LOD, а удалённые объёмные выступы — рисунком на фасаде. Исходные тайлы повторяются в метрах, поэтому сама полоса выступа не размножается. Дальний дом по-прежнему один меш; геометрический силуэт переключается ступенчато. Справочные атласы пересобираются через node scripts/build-building-atlas.mjs; в runtime эти SVG больше не загружаются.


«Солнечные тени» (`shadows`) включаются отдельно: два каскада 1024²/PCF Medium до 96 м по глубине камеры. Вблизи тени подробнее, вдали грубее, переход смешивается — дальние тени сохраняются. Для устройств без CSM используется широкая карта 1024²/160×160. Статичные карты кешируются до изменения камеры/света/геометрии. Мелкие обычные детали отбрасывают тени; дорожные пакеты и широкая земля только принимают их. Подробный контракт — в инструкции shadows.

Модуль **«Загрузка участков»** включается вместе с «Первым кварталом»: создаёт экземпляры секций 128×128 вокруг камеры заранее до 192 м и выгружает после 256 м. LOD и дальность теней сохранены. Начальный вход и телепорт заполняют окружение постепенно, по две секции за кадр. Общие текстуры и описания схемы остаются в памяти; игровые коллизии и файловая/сетевая загрузка пока отсутствуют.

Схема River North подготовлена из официальных данных City of Chicago под MIT. Источник, фиксированная версия и воспроизведение — [описание данных](src/modules/world/data/README.md). Т-образные соединения и длины улиц учитываются генератором; размеры дорог, уклон и здания остаются игровыми.


В категории **«Игра»** включить **«Управление персонажем»**: автоматически подключатся персонаж, симуляция и мир. WASD — ходьба 1.8 м/с, Shift — бег 7 м/с, ПКМ — поворот камеры, колесо — расстояние. Сначала сфокусировать canvas кликом. При фокусе в UI/потере фокуса движение прекращается. Выключение возвращает свободную камеру. «Персонаж» отдельно показывает модель и предоставляет сценарий ▶ без управления.

Позицию определяет headless authority на фиксированных тиках через проверяемые JSON-команды; меш только отображает снимок. Коллизии зданий, фонарей, монумента и площадок не зависят от LOD/выгрузки. Поддержаны уклон и бордюры, камера сокращает дистанцию перед препятствием. Используется CC0-человек с лицом/волосами/одеждой: 5970 треугольников, один skinned mesh/материал, семь скелетных клипов idle/walk/jog/sprint/jump start/loop/land; динамическая физика и реальная сеть пока отсутствуют. Имитатор доставки проверяет задержку/джиттер/потери и перестановку команд в Node-тестах.

Источник модели и анимаций, лицензии и ограничения библиотеки: [human/SOURCES.md](public/models/human/SOURCES.md). Новые файлы взяты у автора Quaternius, не из соседнего проекта. Проверены 43+43 клипа бесплатных наборов; заявленные 120+/130+ относятся к полным отдельным версиям. Игра загружает только подготовленный GLB около 0.8 MB, делит геометрию/атласы между представлениями и не тянет всю библиотеку при старте. Состояние загрузки и стоимость модели доступны через «Детали» персонажа.

Персонаж: Space — прыжок через authority с гравитацией и коллизиями; семь клипов, переходы весов около 150 мс. ▶ модуля «Персонаж» создаёт 16 тестовых людей с бегом/прыжками, общими геометрией/текстурами и отдельными скелетами; основной герой остаётся отдельно. Между людьми пока нет коллизий.

## Реальный центральный участок Чикаго

Модуль окружения **«Центр Чикаго»** (ID world) теперь показывает подготовленный из OSM участок Loop и соседних набережных около 1.86×1.61 км. 734 здания с реальными размещениями и полигональными контурами, 888 дорожных отрезков, соединённые перекрёстки/раздельные картографические проезжие части, переходы, 621 процедурно расставленный светофор и 1302 фонаря. Знаковые Willis/Trump/Marina/Wrigley/Tribune — приближённые модели, остальная застройка объединена по участку/материалу.

Русло вырезано из земли; есть береговые стенки, мостовые кромки, вода и геометрическое дно. Рельеф основан на 81 отсчёте USGS 3DEP, профиль дна процедурный. Часть высот/ширин оценена, все уровни Lower Wacker и точные фасады пока не воспроизведены. Светофоры визуальные, движения транспорта/плавания ещё нет.

[Карта участка](public/maps/downtown.svg), [источники, лицензии и подготовка](src/modules/world/data/downtown/README.md). © OpenStreetMap contributors, ODbL; высоты USGS. Для расширения меняются district.json и исходные данные, затем запускается тот же offline-генератор. В браузере нет запросов к OSM/USGS; секции и ресурсы освобождаются стримером. Старые описания River North ниже/выше относятся к прежнему окружению; текущий контент задаёт data/downtown. Стартовый набор модулей не изменён.

Доводка центра: бордюры имеют настоящую вертикальную грань, уличные поверхности делят общую сетку рельефа. Окна привязаны к каждой стене целыми рядами; добавлены утопленные фасады, основание, матовая крыша/карниз и два сдержанных пояса на главной стене, в тех же mesh-пакетах. Подготовленные количества обновляются при геометрической очистке; актуальны city.json.report и последний PERFORMANCE_BASELINE.

Крупная сетка центра: исходные узлы карты и якоря объектов 1 м, размеры 0.25 м, повороты модулей 15°. Бордюр имеет ширину/подъём 0.25 м и светлый оттенок, отличный от тротуара. Крыши/основания/фасады и остальные несветящиеся поверхности используют общие текстуры с запечённым AO и matching normal maps; однотонные остаются только emissive элементы. Сетка — сознательная адаптация реальной карты, движение персонажа остаётся непрерывным.
