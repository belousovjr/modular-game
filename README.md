# Modular Game

Локальная основа игры без выбранного сеттинга: Babylon.js, TypeScript, Vite, React UI на Radix Themes с иконками Lucide. Без сервера и БД.

Направление развития, границы будущих модулей и этапы постоянного онлайн-мира на основе Чикаго — в [черновике плана](docs/PLAN.md).

## Запуск

Node.js 24.12+:

```sh
npm ci
npm run dev
```

Открыть http://localhost:5175. Мышь вращает камеру, колесо меняет масштаб.

```sh
npm run check
npm test
npm run build
npm run preview
```

## Что уже есть

- Сцена на весь экран, FPS и кнопка «Модули» с закреплённым справа списком категорий; изменение набора сразу пересоздаёт сцену. Игровой режим пока отсутствует, позже он станет отдельным модулем.
- Изменения галочек и статусов применяются сразу; пояснения зависимостей доступны при наведении. Успешное сохранение не создаёт уведомлений, ошибки остаются видимыми.
- Чекбоксы модулей, автоматическое включение зависимостей, запрет отключения используемой зависимости, немедленное сохранение набора в localStorage.
- Кнопка «Детали» у запущенного модуля с инфо-панелью: перемещаемое окно с закрытием. Панель симуляции показывает секунды, тики и задолженность.
- Типизированные зависимости, проверка графа, обратная очистка и обработка неудачного setup.
- Два примера: площадка и зависимый от неё маяк. Его визуальная анимация следует снимку часов симуляции.
- Опциональный модуль симуляции (включён по умолчанию): headless local authority с фиксированными 60 Hz. Задолженность после зависания сохраняется, за кадр обрабатывается не более 240 тиков. Низкий FPS не меняет скорость часов после догоняния.

## Геометрия

Модуль «Геометрия» в категории «Рендеринг» зарегистрирован вне стартового набора. Предоставляет API для потребителей; при включении видимые объекты не появляются. Собственного сценария ▶ нет.

Потребитель объявляет `requires: { geometry: geometryModule }` и вызывает `deps.geometry.createModel(name, parts, scope)`. Деталь содержит имя поверхности `surface`, размер `size: [x,y,z]` и необязательные локальные `position`/`rotation` (радианы). Результат содержит корень `root` и группы мешей `surfaces`. Геометрия общая, преобразования независимы; простое отображение работает без света. Пока поддержаны только прямоугольные детали. Это клиентское представление, не игровое состояние. Контракт — в [инструкции модуля](src/modules/geometry/AGENTS.md).

Отдельный зависимый модуль `materials` для оформления поверхностей и текстур запланирован, ещё не реализован. Шаблоны, LOD и оптимизация draw calls — следующие этапы.

## Добавить модуль

Создать `src/modules/<id>/index.ts` или `index.tsx`, объявить через `defineModule` из `src/core/context.ts`, указать `category` и `requires`, зарегистрировать в `src/registry.ts`. Публичный API возвращается из `setup`, чужой API доступен через `deps`. Все ресурсы регистрируются через `scope.onDispose` сразу после создания. См. площадку и маяк.

Core предоставляет `onFrame` (монотонная разница времени в миллисекундах, до рендера) и `panels`. Для своей инфо-панели передать React-элемент из `setup` и сразу зарегистрировать очистку: `scope.onDispose(core.panels.register('module-id', 'Название', <Info />))`. Core хранит регистрации панелей; React отображает кнопку «Детали», окно и содержимое внутри общей темы Radix, размонтирует панель при очистке. Оболочка UI — `src/main.tsx`, окно — `src/core/panel-window.tsx`. Оформление берётся из компонентов библиотеки, CSS отвечает только за размещение. Состояние и подписки содержимого принадлежат React-компоненту; подписки очищать в `useEffect`. Пример — `src/modules/simulation/index.tsx`. Видимость и положения окон сохраняются в localStorage и восстанавливаются при пересоздании сцены. Перемещение — за заголовок мышью/касанием или стрелками с фокусом на заголовке, закрытие — кнопкой или Escape.

Время доступно через объявленную зависимость `simulationModule` и `deps.simulation.snapshot()`. Маяк требует симуляцию, поэтому отключать её нужно вместе с маяком. Применение набора создаёт новые часы с нуля.

`npm run check` проверяет типы (включая отрицательные тесты) и границы импортов. Это защита от случайных нарушений, а не sandbox для недоверенного кода. Модули — доверенный исходный код проекта.

## Будущий мультиплеер

Сейчас реализованы часы authority, не игровая симуляция и не сетевой протокол. Первая механика должна добавить сериализуемые команды, валидацию на authority и снимки состояния. Будущий сервер владеет игровым состоянием и набором игровых модулей; локальные чекбоксы не смогут менять правила общей сессии. Клиент рисует снимки и отправляет намерения.

`src/simulation` не зависит от браузера и Babylon. Транспорт, сетевой имитатор, prediction/reconciliation и сервер пока отсутствуют. Непрерывная фоновая симуляция браузером не гарантируется. Полные правила развития — в [AGENTS.md](AGENTS.md).

## Сценарии тестирования модулей

Клиентский сценарий `test` необязателен и сейчас задан у маяка и площадки (по 4 секунды замера плюс 1 секунда прогрева): длительность `durationSeconds` и синхронный `setup({ core, deps, api, scope })`, возвращающий функцию `(progress) => void` с прогрессом от 0 до 1. Указывать `test` после основного `setup`, чтобы TypeScript вывел API экземпляра. `core` даёт доступ к сцене, кадровому событию и панелям, `api` — к своему запущенному экземпляру, `deps` — к объявленным зависимостям. Ресурсы и изменения теста очищаются через отдельный `scope.onDispose`, в том числе при неудачном старте. Сценарии выполняются существующим рендер-циклом; бесконтрольные async-задачи не нужны. Будущие игровые действия должны идти командами authority, а не менять мир из теста.

Кнопка ▶ появляется только у модулей со сценарием и запускает его; общий ▶ последовательно запускает доступные сценарии включённых модулей. Маяк демонстрирует двухкруговой облёт с изменением высоты и расстояния, площадка — круговой обзор. Управление камерой и основной UI заблокированы до окончания; кнопка «Остановить» остаётся доступной, включая клавиатуру. Камера и управление восстанавливаются при завершении, отмене и ошибке. Скрытие вкладки отменяет прогон, чтобы фоновые ограничения браузера не искажали FPS. Часы симуляции продолжают идти.

Перед каждым замером — 1 секунда прогрева, которая входит в прогресс, но не в метрики. Измеряются интервалы реальных кадров: средний FPS = число кадров / время, минимум, максимум, медиана FPS, P95 времени кадра в миллисекундах (меньше — лучше), число кадров и измеренное время. На остановке сохраняется частичный результат. Для очереди под текущим прогрессом показывается общий: каждый сценарий занимает равную долю. После прогона панель закрывается крестиком без удаления данных из API; следующий запуск снова её показывает. Для нескольких тестов под таблицей выводится сводка по статусам, кадрам, времени, общему среднему FPS и крайним значениям. Средний FPS сводки считается по суммарным кадрам и времени, а не усреднением средних FPS тестов. Это FPS всей текущей сцены со всеми включёнными модулями и UI во время сценария, а не изолированная стоимость модуля. Результаты живут в памяти до следующего прогона или перезагрузки.

Для автоматизации доступен `window.moduleTests`:

```js
window.moduleTests.list();
await window.moduleTests.run(['beacon'], 10); // 10 с замера + 1 с прогрева
await window.moduleTests.run(); // все запущенные сценарии с их длительностями
window.moduleTests.getState(); // прогресс и сериализуемые результаты
window.moduleTests.stop();
```

Команда `test:modules` запускает Chromium без окна. Чтобы делегировать замер агенту или запустить из терминала, оставить `npm run dev` работающим и выполнить в другом терминале:

```sh
CHROME_BIN=/path/to/chromium npm run test:modules
# Если chromium есть в PATH, CHROME_BIN не нужен.
MODULE_TEST_IDS=beacon MODULE_TEST_SECONDS=10 npm run test:modules
# Для отладки с окном браузера:
node scripts/run-module-tests.mjs
```

Скрипт использует встроенные средства Node и DevTools Chromium, проверяет запуск и остановку кнопками, блокировку UI и прогресс, затем запускает выбранные сценарии и печатает JSON. `MODULE_TEST_URL` меняет адрес приложения (по умолчанию `http://127.0.0.1:5175`). Используется временный профиль с начальным набором модулей и размером viewport 1280×720; профиль удаляется после прогона. `MODULE_TEST_IDS` — ID через запятую; `MODULE_TEST_SECONDS` — длительность каждого замера от 0 до 300 секунд, не включая 0. Ошибка или отмена дают ненулевой код выхода.

Для сравнения FPS сохранять одинаковые браузер, разрешение, набор модулей и окружение. JSON включает разрешение и WebGL renderer: headless-прогон через SwiftShader измеряет программный рендеринг, его нельзя выдавать за производительность пользовательской видеокарты. Частота монитора и VSync тоже ограничивают FPS.

## Общий FPS-прогон

```sh
npm run test:fps
# Аппаратный замер с окном на том же ПК и в доступной графической сессии:
npm run test:fps -- --headed
```

Отдельно запускать dev-сервер не нужно: команда собирает production-версию и поднимает временный сервер на свободном порту. Используется Chromium из `CHROME_BIN`, PATH или установленного Linux-кэша Playwright. Если браузер не найден, указать `CHROME_BIN=/path/to/chrome`.

Команда включает и применяет **все зарегистрированные модули**, включая модули вне стартового набора, затем выполняет все доступные сценарии последовательно. Модули без собственного сценария тоже включены и влияют на производительность сцены. В терминале выводятся только средний FPS каждого сценария и общий средний FPS с цветами по шкале, PASS/FAIL, допустимые градации и renderer. Ошибки показываются отдельно. Полный отчёт версии 2 сохраняется в `artifacts/fps-report.json` (каталог исключён из Git), включая ошибки запуска.

Правило допуска хранится в `fps.config.json`:

```json
{
  "metric": "average",
  "passGrades": ["orange", "yellow", "green"]
}
```

Проверяется общий средний FPS по суммарным кадрам и времени, а не среднее арифметическое FPS сценариев. Градации общие с UI: `<30` — `red`, `30…<60` — `orange`, `60…<90` — `yellow`, `≥90` — `green`. Текущий конфиг пропускает средний FPS от 30; остальные метрики выводятся для информации и не определяют допуск. Градация определяется до округления. Для изменения допуска редактировать `passGrades`; пока поддерживается только метрика `average`.

Код выхода: `0` при успешных сценариях, наличии измерений и разрешённой градации; `1` при провале правила, ошибке, отмене, отсутствии замеров или некорректном конфиге. JSON содержит применённое правило `policy` и фактическую `grade`. Старый `FPS_MIN_AVERAGE` больше не используется. Автоматическую блокировку слияний нужно подключить к этому коду выхода в CI и настройках репозитория.

Для аппаратного прогона в текущем WSL-окружении проверена команда (переменные действуют только на процесс):

```sh
GALLIUM_DRIVER=d3d12 MESA_D3D12_DEFAULT_ADAPTER_NAME=NVIDIA MODULE_TEST_SECONDS=10 npm run test:fps -- --headed
```

Условия и ограничения исходного замера — в [базовой линии](docs/PERFORMANCE_BASELINE.md). Выбор драйвера выше относится к этому ПК/WSL, не является универсальной настройкой для всех ОС.

По умолчанию прогон headless. `--headed` запускает окно без разрешения на SwiftShader; фактический WebGL renderer всё равно нужно проверить в отчёте. JSON фиксирует `environment.headless`. Аппаратные замеры сравниваем на одном ПК, с одинаковыми GPU, браузером, графической сессией, питанием и разрешением; WSL/WSLg отмечаем отдельно от нативного Windows-браузера.

Изоляция: новый временный профиль браузера, viewport 1280×720; личный localStorage не меняется. `MODULE_TEST_SECONDS` переопределяет длительность каждого замера, но `MODULE_TEST_IDS` запрещён, чтобы прогон оставался полным. Сервер и браузер автоматически закрываются. Для сравнения веток использовать одинаковый runner и renderer: программный SwiftShader не является замером физической GPU.

Панель модулей разделена на вкладки «Рабочие», «Скрытые» (кандидаты в core, всегда включены) и «Архив» (кандидаты на удаление, всегда отключены). Меню троеточия меняет статус; вкладка и статусы сохраняются локально. Изменение состава сцены применяется сразу с её пересозданием; кнопки применения нет. Над вкладками находятся общий тест и сброс стартового набора, статусов и вкладки. Обзор камеры сохраняется при изменении модулей и между перезагрузками; сброс модулей возвращает камеру в исходное положение. Архивировать обязательные модули и зависимости включённых модулей нельзя. Скрытые и архивные не перечисляются в тултипах зависимостей. Статусы не переносят и не удаляют код.

Шестерёнка справа от «Модули» открывает экспорт/импорт персональных настроек в файлах `.mgeng` (обычный JSON внутри). Ctrl+Z отменяет изменения набора модулей и их статусов, Ctrl+Shift+Z возвращает их; история сохраняется в localStorage. Окна, категории и вкладки сохраняются автоматически и не входят в историю или признак несохранённых изменений. Ctrl+S сохраняет текущие настройки в IndexedDB. Звёздочка в начале заголовка страницы означает несохранённые изменения; после сохранения исчезает. Ошибки показываются текстом. Импорт обновляет localStorage, интерфейс и IndexedDB и может быть отменён. Экспорт включает только набор модулей и их статусы. Положение и видимость окон, вкладка, свёрнутые категории, камера, история и игровой мир в файл не входят; импорт сохраняет текущий интерфейс. Камера сохраняется отдельно только в localStorage, не участвует в undo/redo и не влияет на звёздочку; её сбрасывает только кнопка дефолтов. Во время тестов команды недоступны.
