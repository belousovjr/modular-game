# Клиентская инфраструктура core

`context.ts` задаёт `CoreContext`: Babylon `scene`, кадровое событие `onFrame` с монотонной разницей времени в миллисекундах и `panels`. `defineModule` создаётся через `moduleFactory<CoreContext>()`. Потребители — клиентские модули; сборка приложения и регистрация находятся в `src/main.tsx` и `src/registry.ts`.

## Контракты и жизненный цикл

Core не создаёт источники освещения: ими владеют клиентские визуальные модули. Сцена без выбранного освещения не получает скрытый источник света.

- `modules.ts`: определение модуля содержит `id`, `title`, `category`, `requires`, `setup`, опциональные `required` и `test`. `setup` возвращает API экземпляра. `resolveModules` проверяет определения зависимостей по ссылке и возвращает порядок запуска. `startModules` возвращает `ids`, `tests` и `dispose`; зависимости передаются в `deps`, ресурсы основной сессии очищаются в обратном порядке, включая частичный сбой запуска.
- `scene.ts`: `createViewport` владеет движком, камерой, сценой, render loop и тестовым runner. В кадре сначала уведомляется `onFrame`, затем рисуется сцена, затем продвигается тест. `restart` пересоздаёт сцену и модули, во время теста запрещён. `dispose` останавливает тест, очищает сессию, обработчики, observer и движок.
- `panels.ts`: `register(id, title, content)` возвращает очистку регистрации. `toggle` и `close` управляют видимостью; `usePanels` подписывает React через внешний store. Удаление регистрации не стирает сохранённую видимость. `panel-window.tsx` отвечает за перемещение мышью и клавиатурой, ограничение позиции границами сцены, закрытие и возврат фокуса. Панели принадлежат модулям, оболочка окна — core.
- `settings.ts` хранит версионированный набор включённых ID и свёрнутых категорий; `window-settings.ts` — видимость и координаты окон. Повреждённые данные и недоступность localStorage обрабатываются без падения приложения.
- `module-categories.ts`: категории сортируются по числу уникальных прямых и косвенных зависимостей, затем по убыванию числа модулей, затем по названию. Внутри категории — по числу зависимостей и названию. Это порядок UI, не запуска. Формат списков для тултипов: модули одной категории вместе, категория в скобках, каждая группа с новой строки.

## Сценарии тестирования

`test` необязателен: добавлять сценарий только при необходимости; модули без него не получают кнопку запуска и пропускаются общим прогоном. `test` объявляется после основного `setup`, чтобы TypeScript вывел собственный API: `durationSeconds`, синхронный `setup({ core, deps, api, scope })`, возвращающий `(progress) => void` с прогрессом 0…1. `api` — собственный запущенный экземпляр, `deps` сохраняет ограничения объявленных зависимостей. `startModules` связывает сценарии с экземплярами, а runner предоставляет отдельный scope для ресурсов и временных изменений теста.

`test-runner.ts` запускает сценарии последовательно в существующем render loop. Длительность замера — больше 0 и не больше 300 секунд, перед каждым замером 1 секунда прогрева; первый интервал после setup не измеряется. В метрики входят только целые интервалы кадров после прогрева: средний FPS по общему времени, минимум, максимум, медиана, P95 времени кадра, количество кадров и измеренное время. Это производительность всей включённой сцены с UI. Частичные результаты сохраняются при остановке; ошибка прерывает очередь. Scope и управление очищаются при завершении, отмене и ошибке, включая ошибку setup или очистки.

`scene.ts` отключает ввод камеры и восстанавливает её состояние; `src/main.tsx` блокирует основной UI через `inert`. `test-panel.tsx` показывает прогресс текущего сценария, а для очереди — дополнительный общий прогресс (каждый тест занимает равную долю). Кнопка остановки доступна с клавиатуры. После окончания прогона результаты можно скрыть крестиком; данные в runner сохраняются, новый запуск снова показывает панель. Для нескольких результатов под таблицей выводится сводка: количества завершённых, остановленных и ошибочных тестов, кадры, измеренное время, общий средний FPS по суммарным кадрам и времени, минимум и максимум. Расчёт сводки — `test-summary.ts`; медианы и перцентили отдельных тестов не усреднять. Скрытие вкладки отменяет тест; часы симуляции продолжают идти.

Viewport предоставляет `tests.list()`, `run(ids?, durationSeconds?)`, `stop()`, `getState()`. Оболочка приложения публикует этот API как `window.moduleTests` и удаляет при очистке. `run` использует только сценарии запущенных модулей, возвращает Promise с сериализуемыми результатами; повторный параллельный запуск отклоняется.

`npm run test:modules` запускает `scripts/run-module-tests.mjs --headless` без окна браузера: нужен работающий dev-сервер и Chromium (`CHROME_BIN` или `chromium` в PATH). Скрипт проверяет кнопки одиночного и общего запуска, остановку, текущий и общий прогресс, блокировку и восстановление UI, затем выполняет сценарии, проверяет сводку и закрытие результатов и печатает JSON с окружением. Использует временный профиль и viewport 1280×720. Ошибка или отмена дают ненулевой код выхода. Параметры запуска описаны в README. Программный SwiftShader нельзя выдавать за замер пользовательской GPU.

При изменении этих контрактов проверять потребителей в модулях, `src/main.tsx`, браузерном скрипте и тестах. Проверки runner находятся в `tests/test-runner.test.ts`, графа и очистки менеджера — в `tests/core.test.ts`, границ типов — в `tests/types.test.ts`.

FPS в таблице и сводке отображается стандартными Radix Badge с общей шкалой `fps-color.ts`: меньше 30 — red, 30…<60 — orange, 60…<90 — yellow, от 90 (включая выше 120) — green. Градация определяется исходным значением до округления. Отсутствующие метрики остаются прочерком; шкалу FPS не применять к миллисекундам P95.

`npm run test:fps` — режим того же браузерного скрипта `--fps`: собирает production-приложение, запускает временный preview на свободном localhost-порту, через UI включает и применяет весь реестр (не только стартовый набор), выполняет все доступные сценарии. Модули без собственного `test` остаются включёнными в сцене. Chromium ищется через `CHROME_BIN`, PATH и Linux-кэш Playwright; новые зависимости не нужны. Используется headless-режим, временный профиль и тот же viewport. Сервер, Chromium и профиль очищаются после выполнения.

Сводка CLI и JSON версии 2 в `artifacts/fps-report.json` включают все включённые ID, результаты сценариев, окружение, общий средний FPS по кадрам и времени, крайние значения и статусы. Правило допуска хранится в корневом `fps.config.json`: `metric: "average"`, `passGrades: ["orange", "yellow", "green"]`. Проверяется только общий средний FPS с общей шкалой `fps-color.ts`, до округления; текущий допуск — от 30 FPS. Список градаций должен быть непустым, без повторов, из red/orange/yellow/green; неподдерживаемые метрики и неизвестные поля конфигурации отклоняются. Ошибка, отмена, отсутствие замеров, недопустимая градация или некорректный конфиг дают код 1, иначе 0. JSON включает `policy` и `grade`. `FPS_MIN_AVERAGE` больше не используется. Ошибка запуска тоже сохраняется в JSON как `passed: false`. `MODULE_TEST_IDS` в этом режиме запрещён, `MODULE_TEST_URL` не используется; `MODULE_TEST_SECONDS` может переопределить длительность всех сценариев. Расчёт и проверка отчёта — `scripts/fps-report.mjs`, тесты — `tests/fps-report.test.ts`. Артефакты не коммитятся. Одинаковые renderer, разрешение и runner обязательны для осмысленного сравнения порога в CI; само ограничение слияния настраивается отдельно в CI/репозитории.

Вывод `test:fps` в терминал — таблица с выровненными колонками «Module» и «Average FPS», строкой «Total» и отдельным итогом PASS/FAIL: общий и посценарный средний FPS, цвет по общей шкале (orange — ANSI yellow, yellow — bright yellow), PASS/FAIL, допустимые градации, окружение, ошибки и путь к JSON. Остальные метрики сохраняются в JSON. Цвета через Node `styleText`, с учётом поддержки терминала.

## Локальные статусы модулей

`module-preferences.ts` хранит персональные статусы `working`, `hidden`, `archived` и активную вкладку в `modular-game.module-preferences` (версия 1). Неизвестные ID/статусы отбрасываются, повреждённые данные сбрасываются. Архивные зависимости required/hidden при чтении возвращаются в рабочие. Это локальная организация списка, не серверная конфигурация или фактический перенос кода в core.

`selectModules` добавляет hidden и required, исключает archived и рабочие модули с архивными зависимостями. Конфликт принудительного включения с архивом отклоняется. Менеджер и публичный контракт модулей не изменены. В UI три вкладки Radix Tabs и меню Radix DropdownMenu: из рабочих — «Скрыть» или архивирование, из остальных — возврат в рабочие. Архивирование required и зависимостей включённых потребителей запрещено, включение потребителя архивной зависимости недоступно. Галочки и статусы применяются синхронно и сохраняются сразу; при изменении включённого набора сцена пересоздаётся. Если новый набор не запускается, оболочка пытается восстановить предыдущий набор и показывает ошибку; при ошибке восстановления управление набором и тестами блокируется до перезагрузки. Переключение вкладки не пересоздаёт сцену. Возврат из архива сам по себе модуль не включает. Кнопки применения нет. Над вкладками расположены общий тест и сброс: сброс немедленно возвращает defaultModules, все статусы в working и вкладку working, сбрасывая камеру. Списки зависимостей и потребителей в тултипах содержат только working; ограничения учитывают все статусы.

Проверки политики и чтения настроек — `tests/module-preferences.test.ts`. В браузере проверить меню, вкладки с клавиатуры, перезагрузку, применение статусов, исключение скрытых/архивных из тултипов, запреты при зависимостях и ошибки storage. FPS-прогон с чистым профилем продолжает включать весь реестр.

Кнопка теста модуля остаётся видимой, но недоступна, если модуль выключен. Снятие галочки сразу останавливает модуль и блокирует его тест. Браузерный runner проверяет немедленное выключение и повторное включение сценария через галочку.

## Сохранение камеры

`camera-settings.ts`: `modular-game.camera`, версия 1, alpha/beta/radius и target x/y/z. Чтение проверяет конечные числа, beta в (0, π), radius 3…35; повреждённые или недоступные данные игнорируются. `scene.ts` переносит текущий обзор при restart, восстанавливает сохранённый при первом запуске. Сохранение изменённого обзора — не чаще раза в 500 мс, а также при restart, скрытии вкладки и dispose. Во время теста сохранение пропускается, после остановки сохраняется восстановленный пользовательский обзор. Это только клиентская настройка отображения. Проверки storage — `tests/camera-settings.test.ts`; в браузере проверить смену модулей, перезагрузку и сохранение пользовательского обзора после теста.

`restart(registry, selected, resetCamera = false)` сохраняет обзор по умолчанию; флаг true пересоздаёт сцену с исходной камерой и сразу записывает её в storage. Кнопка сброса вызывает этот режим даже при неизменном наборе модулей.

## История и сохранение персональных настроек

`settings-history.ts` — единственная точка записи отслеживаемых настроек: modules, categories, module-preferences и window.* (камера пишет отдельно напрямую в localStorage). Писать через `settingsHistory.write`, составное действие оборачивать в `transaction`. История снимков только набора модулей и статусов и курсор хранятся в `modular-game.history` (версия 1); несовместимая, повреждённая или не соответствующая текущему снимку история игнорируется. Новый шаг после undo удаляет redo-ветку. Окна (видимость и позиции), категории и активная вкладка не создают шаги и не влияют на dirty. Они сохраняются автоматически в localStorage; перетаскивание пишет позицию после отпускания указателя. Старые UI-шаги удаляются из истории с сохранением курсора. Действия runner и время симуляции не входят в историю. Ошибка записи истории показывается пользователю, история остаётся в памяти; при исчерпании квоты нет тихого удаления шагов.

`SettingsMenu` справа от активатора модулей показывает только экспорт/импорт без отдельного индикатора около кнопки. Несохранённые настройки обозначаются единственной `* ` в начале document.title; при совпадении с сохранением звёздочка убирается. До чтения сохранения заголовок не помечается; при размонтировании исходный заголовок восстанавливается. Ошибки остаются текстом. Это отдельный подписчик `useSyncExternalStore`: обновление заголовка не сканирует storage и не пересчитывает историю на рендерах/FPS. Ctrl/Cmd+Z и Ctrl/Cmd+Shift+Z восстанавливают предыдущий/следующий снимок и актуализируют только набор модулей и статусы, сохраняя текущий интерфейс и камеру без перезагрузки страницы. Нативный undo текстовых полей не перехватывается. Во время тестов команды заблокированы. Восстановление не пишет новые шаги; при ошибке пытается вернуть прежний снимок.

`settings-database.ts` использует IndexedDB `modular-game` v1, object store `settings`, ключ `current`, значение `{version:1, settings}`. Ctrl/Cmd+S захватывает текущий снимок без камеры, сохраняет асинхронно и отмечает сохранение только после transaction.oncomplete. Правки во время сохранения остаются несохранёнными. При запуске БД читается для сравнения, не заменяет localStorage автоматически. Нет сохранения мира или результатов тестов.

Экспорт `modular-game-settings.mgeng` (обычный JSON `{version:1, settings: Record<string,string>}`; фильтр импорта `.mgeng`) содержит только набор включённых модулей и статусы. `exportSettingsSnapshot` исключает категории, окна, их положения, вкладку, камеру, историю и метаданные. Импорт проверяет версии, разрешённые ключи и структуру значений, через `mergeImportedSettings` заменяет только данные модулей в localStorage, сохраняя текущую вкладку, категории, окна и их позиции, затем актуализирует интерфейс и сохраняет применённый снимок в IndexedDB. Старые UI-поля в файле игнорируются. Интерфейс хранится автоматически в localStorage и может попадать в снимок Ctrl+S, но не участвует в undo/redo, dirty и файловом обмене. Для сравнения с сохранением и истории используется проекция `exportSettingsSnapshot`; `capture` возвращает текущие локальные настройки без камеры. Восстановление накладывает данные модулей на актуальные UI-настройки. Импорт — один отменяемый шаг. Если БД отказала после применения импорта, локальные изменения остаются и ошибка видна; Ctrl+S позволяет повторить сохранение. Undo импорта не меняет сохранённый снимок БД до следующего Ctrl+S. Посторонние ключи localStorage не трогаются.

Проверки истории, группировки, отката, ветвления, повреждённых данных и ошибок квоты — `tests/settings-history.test.ts`. Браузерный runner проверяет Ctrl+S с реальной IndexedDB, индикатор, undo/redo вкладок и модулей, экспорт, импорт с обновлением обоих хранилищ и сохранением независимой камеры и восстановление истории после перезагрузки. Вкладки имеют manual activation: стрелки перемещают фокус, Enter/пробел выбирает вкладку; восстановление браузерного фокуса не создаёт новый шаг истории. При изменении добавить проверки соответствующих настроек и отказов. Камера не входит в снимки, undo/redo, экспорт, импорт, IndexedDB и индикатор изменений. Сохраняется отдельно в localStorage при движении и смене сцены; только явный сброс к дефолтам возвращает исходный обзор. Старые файлы и сохранения с ключом камеры читаются с игнорированием этого ключа; старая запись IndexedDB при чтении перезаписывается без камеры. История мигрирует с удалением ключа камеры и последовательных дублей шагов, сохраняя курсор. Старое положение камеры в localStorage не удаляется.

В панели результатов вертикальная прокрутка ограничена `Table.Body` (строки, максимум min(240px, 25dvh)); заголовок таблицы, прогресс и сводка находятся вне неё. Колонки заголовка и строк имеют одинаковую фиксированную раскладку и gutter. Горизонтальная прокрутка всей таблицы остаётся штатной Radix Table (минимальная ширина 900px). Тело таблицы доступно для фокуса и прокрутки клавиатурой. Браузерная проверка добавляет временные строки, проверяет высоту и неподвижность заголовка/сводки при прокрутке, затем удаляет их.
